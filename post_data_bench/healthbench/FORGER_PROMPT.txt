# Task: Clinical Assistance for Physicians

You must produce a demonstration of how to effectively and extensively use a new data generation library called Forger. You will show that your demonstration is effective by generating a training dataset to finetune a small reasoning model to get better at assisting physicians. The dataset must consist of prompts and rubrics, which can be used to perform RL training (GRPO) on the small model. You have {TIMEOUT_HOURS} hours and are welcome to iterate as time allows before selecting and submitting a final RL checkpoint for evaluation.

In this setup, a model is given a chat between a physician and an assistant, ending in the physician's message, and must write the assistant's next reply in a single response, with no tools and no feedback. The chats are physicians' own tasks: consults about patients, writing and documentation, and questions about medical research; some test whether the assistant handles unsafe, misleading or underspecified requests well. Most chats are a single message, some have earlier turns, and they range from a few words to long pasted notes or papers. Each chat has its own rubric written by physicians: one to five criteria, each worth between -10 and 10 points. Positive criteria describe what a good reply does; negative criteria describe mistakes, such as unsafe advice. A grader model checks each criterion separately against the final answer only (the text after the last </think>; the reasoning is never graded) and decides whether it is met. An answer's score is the sum of the points of the criteria it meets (met negative criteria subtract) divided by the sum of the positive points, so it can be below 0. The score is then adjusted for length: it loses 0.0147 for every 500 characters of final answer beyond 2,000, and gains the same for every 500 characters short of 2,000. A chat's score is the mean over 8 independently sampled answers, and performance is the mean chat score, clipped to [0, 1] and multiplied by 100.

Your data should make the model's replies better as physicians judge them.

The validation set is yours to use however you like. It consists of:
- {TASK_DIR}/validation_tasks.jsonl: one row per chat, with "id", "messages" (the chat, ending in the physician's message), "rubric_items" (its criteria, each {{"criterion_text", "points"}}), and "physician_response" (a physician's own reply to the chat).
- {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/, if present: the baseline model's results, graded with the same judge as `evaluate_model.sh`. metrics.json holds summary scores. In predictions.jsonl, each row's "samples" holds its sampled answers, and each answer's "criteria" gives, for every criterion, whether it was met and the grader's explanation.

"messages" is exactly what a model sees at evaluation, with no system message (`prompt_building.build_candidate_prompt(messages)` in {TASK_DIR}/prompt_building.py returns it). Each answer is sampled at temperature 1.0 with up to 28,672 tokens; a response that runs out of tokens before closing its reasoning is graded as an empty answer. The grader's prompt is `GRADER_TEMPLATE` in {TASK_DIR}/judge.py, and `bash {TASK_DIR}/evaluate_model.sh` runs the whole evaluation (see Training and Validation). Your prompts are used verbatim for training.

# Data Format

Write ONE dataset to {RAW_DATA_PATH} (write a temporary file, then rename it). Each JSONL row has the fields "prompt" and "rubric", and optionally "ground_truth":
{{"prompt": [{{"role": "system", "content": "..."}}, {{"role": "user", "content": "..."}}], "ground_truth": "a reference answer (optional)", "rubric": [[{{"prompt": "Describe a criterion for the judge", "answer_only": true}}, 1.0], [{{"code": "def grade(prompt, response, ground_truth):\n    return 1.0"}}, 1.0]]}}
The constant score above only illustrates syntax; use meaningful criteria.

- "prompt" is the chat messages, ending in a user turn. RL samples responses to these messages; neither the ground truth nor the rubric is ever shown to the policy.
- "ground_truth" is optional text that your criteria receive, for example a reference answer; it is "" when omitted. Training uses only prompts and rubrics, so rows need no written responses. The student model ({STUDENT_MODEL}) is trained and evaluated in thinking mode; only the text after the final </think> is graded.
- "rubric" is a nonempty list of [criterion, weight] pairs with finite weights whose positive weights have a positive sum. The RL reward is (sum of weight x criterion score) / (sum of the positive weights), clipped to [0, 1], so a criterion with a negative weight lowers the reward when the response does what it describes, e.g. [{{"prompt": "States a wrong final answer"}}, -2]. The judge never sees weights: it judges whether the response does what the criterion describes. Each criterion is either:
  - {{"code": ...}}: Python defining one top-level `def grade(prompt, response, ground_truth):` (three positional parameters) that returns a number in [0, 1]. `prompt` is the chat messages; `response` includes its thinking trace. It runs in RestrictedPython: only json, re, math, string, collections, itertools, functools, and statistics can be imported, with no files or network; names starting with "_" (`_` alone works), `nonlocal`, annotated assignments, `str.format`, and `open()` fail, and a criterion that fails scores 0 for every response. grade() can also call `final_answer(response)`, the text after the last `</think>` ("" while a `<think>` is still open); call it rather than writing the tags, which the LLM gateway can rewrite in model-written code. From {TASK_DIR}: `python rl/rubric_worker.py < criterion.json` (a JSON object with "code", "prompt", "response", and "ground_truth") prints the score RL would give.
  - {{"prompt": ...}}: a natural-language criterion. The judge model (DeepSeek-V4.1-Flash) scores it given the criterion, the prompt, the full response, and the ground truth. With {{"prompt": ..., "answer_only": true}}, the judge sees only the final answers instead: the text after the last </think> of the response and of the ground truth ("" when the response's thinking is never closed), which costs far fewer judge units on long responses. For this task the defaults are different: unless a criterion sets these options itself, "answer_only" is true and "judge_sees" is ["response"], so the judge receives only the criterion and the final answer (no chat, no ground truth, no thinking). Two more options shape what the judge gets: "judge_sees" lists which of "prompt", "response" and "ground_truth" it receives (it must include "response"; ["response"] by default for this task), so {{"prompt": ..., "judge_sees": ["response"]}} sends neither the chat nor the ground truth; and "instructions" is text of up to 4,000 characters added to the judge's system message for that criterion only. "scale" sets how the judge answers: "binary" (the default) asks yes or no, scored 1 or 0, and "likert" asks an integer from 1 (not at all) to 5 (fully), scored 0, 0.25, 0.5, 0.75 or 1; instructions cannot change the scale. "n" is a positive integer (default 1): e.g. {{"prompt": ..., "n": 3}} requests three judgments in one call and averages their scores before weighting. Binary votes remain 0 or 1, but their average can be fractional. More samples consume more judge quota and may reduce sampling noise; they do not guarantee correction of systematic errors. Code criteria may return any value in [0, 1]. The RL judge scores each criterion from 0 to 1 with its own prompt (`prompt_score` in {TASK_DIR}/rl/rubric_rm.py); the evaluation grader decides met or not met. When the provider's content filter blocks the judge's reply, that criterion is ungraded and RL does not train on that response (e.g. a sampled answer that goes along with an unsafe request).

Submit at least 10 and at most 2,000 rows, with no duplicate prompts; 2,000 is a hard limit. Submit at least 400 rows, and more if you can. The default RL recipe draws {RL_PROMPT_DRAWS} prompts and samples 8 completions per prompt ({RL_COMPLETIONS} completions total). Prompts are drawn repeatedly from the training partition; a small dataset is revisited more often. You may revise your data and run RL as often as your time and quotas allow.

Your model will be tested on a public benchmark of physician-written chats and rubrics, the same one the validation chats come from. Study the validation set freely and let it guide your data; the benchmark itself is off-limits. Do not search for, download, or browse it. Do not train on its chats (or ones you suspect are in it), their rubrics or reference answers, or edited versions of them, and do not try to reconstruct it or work out which chats it contains. General public material such as clinical guidelines, textbooks, drug references, and research papers is fine. The training commands remove rows that overlap the benchmark and report how many they removed; `python -m rl.decontaminate --data <file>` (from {TASK_DIR}) reports the same count for any file. Use it sparingly, to check your own data, never to probe what the test set contains. Breaking any of these rules fails your run automatically, without notice. The goal is a model that is genuinely strong at this kind of chat, not one that has memorized the benchmark.

Each prompt must fit in {MAX_SFT_LENGTH} tokens; longer rows are rejected, not truncated. The harness holds out a fixed 10% of your rows to monitor RL reward and trains on the rest; do not generate a separate evaluation set.

Check the format before training and again after your last edit (from {TASK_DIR}):
python -m rl.agent_training validate --data {RAW_DATA_PATH}
This checks the schema, weights, thinking targets, grade() signatures, and RestrictedPython compilation. It does not run criteria or call the judge. It prints the row count.

# LLM API Usage

Generation has a shared quota of {GENERATION_TOKEN_UNIT_LIMIT} token units. DeepSeek-V4-Flash costs 1 unit per input token and 3 units per output token; GLM-5.3 costs 4 units per input token and 12.5 units per output token. Count cached inputs at full weight and include reasoning in output tokens. Use `litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731` or `litellm_proxy/azure_ai/FW-GLM-5.3`; other model families have no defined unit weights for this run.

Read `{GENERATION_USAGE_PATH}` for cumulative `token_units`, `remaining_token_units`, and `cost_usd`. `unpriced_calls` counts responses without dollar pricing; only token units enforce the quota. The quota spans all pipeline iterations and processes. Each call holds its worst case in the shared ledger while it is in flight (its prompt plus `max_tokens` for every completion, or 65,536 tokens per completion without `max_tokens`), and new calls stop once used plus held units reach the quota. A response replaces its hold with its actual usage. A call that times out, loses its connection, or is still running when its process is killed stays charged at its full hold, because the API may still bill it; the ledger counts these in `unreturned_calls` (a killed process's holds move there after two hours). Setting `max_tokens` keeps holds close to real usage. Do not delete/reset the ledger or change its environment settings. The OpenHands model driving your agent turns is accounted separately.

Credentials are provided as `LITELLM_API_KEY` and `LITELLM_BASE_URL`; load them from the environment without printing them. Forger's Model records usage against this quota automatically, so make your generation calls through Forger and do not wrap Model calls a second time. LLM calls you make outside Forger (e.g. with litellm directly) are counted only through `completion` or `acompletion` from `rl.token_budget` (in {TASK_DIR}) with budget="generation"; they make one attempt per call (no `num_retries`), so retry in your own code.

DeepSeek-V4-Flash returns its reasoning separately from its answer, and Forger keeps it: `sample_from_LLM` and `generate_from_context` put it under each output's `thinking_trace` key. Set the effort explicitly, e.g. `Model(..., reasoning_effort="high")`: without it DeepSeek-V4-Flash does not think at all, and the setting controls how long the reasoning is.

Measured on this gateway: GLM-5.3 still reasons with an effort of "none" (as at "low"); on hard prompts, DeepSeek-V4-Flash at "low" reasoned 10,000-25,000 tokens, and either model can spend all of `max_tokens` on reasoning and return no answer. Long GLM-5.3 requests can time out at the gateway.
