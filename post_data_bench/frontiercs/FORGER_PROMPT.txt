# Task: Open-Ended Algorithmic Programming

You must generate a training dataset to finetune a small reasoning model to get better at open-ended algorithmic programming. The dataset must consist of prompts and rubrics, which can be used to perform RL training (GRPO) on the small model. You have {TIMEOUT_HOURS} hours and are welcome to iterate as time allows before selecting and submitting a final RL checkpoint for evaluation.

In this setup, a model is given a problem statement and must answer, in a single response with no tools and no feedback, with one self-contained C++17 program. Most problems have no single correct output: they are optimization, construction, or interactive problems, and an answer earns partial credit for how good it is. The statement gives the input and output format and how an answer is scored. Each problem has one time limit and one memory limit for all its tests, enforced as in the benchmark: the time limit is CPU time per test (a run is also killed at twice it in wall-clock time), the memory limit caps address space and stack (peak resident memory in interactive problems), and compilation gets 10 seconds of CPU. Every prompt ends with the enforced limits, and they take precedence over the statement, which may omit them or give different ones. The program is compiled with `g++ -O2 -std=gnu++17` and run on every test of the problem, with the test's input on stdin. In an interactive problem, the program instead talks to an interactor program over stdin and stdout, so it must flush its output after every message. A checker or interactor then scores each test between 0 and 1: matching a strong reference answer is worth 0.6, beating it is worth more on a logarithmic scale (capped at 1), and weaker answers earn less, down to 0. A test scores 0 when the program does not compile, exceeds the time or memory limit, crashes, or produces an invalid answer. An answer's score is the mean over its tests, times 100; a problem's score is the mean over 5 independently sampled answers, and performance is the mean problem score.

Every test counts equally, so an answer that is valid and reasonable on every test can outscore one that is excellent on some tests but invalid, too slow, or crashing on others. Your data should make the model's programs better: reading the statement and its scoring rule carefully, producing valid output every time, staying within the limits, and finding better solutions with good algorithms and heuristics.

The validation set is yours to use however you like. (Training on validation problems is allowed, but leaves validation much less useful for choosing checkpoints.) It consists of:
- {TASK_DIR}/validation_tasks.jsonl: one row per problem, with "id", "type" ("default" or "interactive"), "n_tests" (how many tests it is judged on), "time_limit_s", "memory_mb", "statement", and "task_text" (the exact prompt, described below).
- {TASK_DIR}/problems/<id>/: each problem's judging files: config.yaml (its limits), testdata/ (every test's input and answer), and the source of its checker (chk.cc) or interactor (interactor.cc), written with {TASK_DIR}/testlib/testlib.h.
- {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/, if present: the baseline model's results. metrics.json holds summary scores. In predictions.jsonl, each row's "samples" holds its sampled answers, and each answer's "cases" gives, for every test, its file in testdata/, its status and score, and the start of the checker's or interactor's message.

"task_text" is the exact user turn a model sees at evaluation (the "question" field in predictions.jsonl is the same text): "Problem:", the statement, a "Judging limits ..." line with the enforced limits and the compiler, and "Generate solution code:", separated by blank lines. Before it comes a fixed system message (`SYSTEM_PROMPT` in {TASK_DIR}/prompt_building.py) asking for only C++ code in a ```cpp fence. Each answer is sampled at temperature 1.0 with up to 16,000 tokens. The evaluator judges the longest ```cpp block after the final </think>, or the longest one in the reasoning if the response runs out of tokens before closing it; a response with no code block scores 0. Your prompts are used verbatim for training, and a different format will not transfer to evaluation, so build them the same way: `prompt_building.build_candidate_prompt(prompt_building.build_user_content(statement, time_limit_s, memory_mb))` returns the system message and the user turn.

# Data Format

Write ONE dataset to {RAW_DATA_PATH} (write a temporary file, then rename it). Each JSONL row has the fields "prompt" and "rubric", and optionally "ground_truth":
{{"prompt": [{{"role": "system", "content": "..."}}, {{"role": "user", "content": "..."}}], "ground_truth": "a reference answer (optional)", "rubric": [[{{"code": "def grade(prompt, response, ground_truth):\n    return 1.0"}}, 1.0], [{{"prompt": "Describe a criterion for the judge"}}, 1.0]]}}
The constant score above only illustrates syntax; use meaningful criteria.

- "prompt" is the chat messages, ending in a user turn. RL samples responses to these messages; neither the ground truth nor the rubric is ever shown to the policy.
- "ground_truth" is optional text that your criteria receive, for example a reference answer (one complete C++17 program in a ```cpp fence); it is "" when omitted. Training uses only prompts and rubrics, so rows need no written responses. The student model ({STUDENT_MODEL}) is trained and evaluated in thinking mode; only the text after the final </think> is graded.
- "rubric" is a nonempty list of [criterion, weight] pairs with finite, nonnegative weights and a positive sum. The RL reward is the weighted mean of the criterion scores. Each criterion is either:
  - {{"code": ...}}: Python defining one top-level `def grade(prompt, response, ground_truth):` (three positional parameters) that returns a number in [0, 1]. `prompt` is the chat messages; `response` includes its thinking trace. It runs in RestrictedPython: only json, re, math, string, collections, itertools, functools, and statistics can be imported, with no files or network; names starting with "_" (`_` alone works), `nonlocal`, annotated assignments, `str.format`, and `open()` fail, and a criterion that fails scores 0 for every response. grade() can call `judge_cpp(code, tests, checker=None, interactor=None, time_limit=1.0, memory_mb=256, details=False)`, which compiles and judges a C++ program as the evaluator does. `tests` is a list of {{"input": stdin, "answer": answer file, "args": [command-line arguments]}} ("answer" and "args" are optional; without "answer", a clean run passes). `checker` or `interactor` is testlib C++ source (with neither, the output must equal the answer up to whitespace) that scores a test by exiting with `quitf(_ok, ...)` (1), `quitp(x, ...)` printing `Ratio: <x>` (x), or `quitf(_wa, ...)` (0). It returns (mean score, per-test statuses), or with `details=True` (mean score, one {{"status", "ratio", "time", "stdout", "message"}} dict per test). Each criterion gets 20 seconds in total, compilation included, and runs on every sampled RL response, so use a few small, fast tests. From {TASK_DIR}: `from rl.rubric_sandbox import Sandbox` gives `Sandbox().judge_cpp(...)`; `python rl/rubric_worker.py < criterion.json` (a JSON object with "code", "prompt", "response", and "ground_truth") prints the score RL would give; and `from rl.solution_runner import score_targets` scores each row's ground_truth with its own code criteria (`score_targets(rows)`), so a target that scores lower than you expect has a rubric, checker, or program that fails in RL.
  - {{"prompt": ...}}: a natural-language criterion. The judge model (DeepSeek-V4-Flash) scores it given the criterion, the prompt, the full response, and the ground truth. With {{"prompt": ..., "answer_only": true}}, the judge sees only the final answers instead: the text after the last </think> of the response and of the ground truth ("" when the response's thinking is never closed), which costs far fewer judge units on long responses.

Submit at least 10 and at most 800 rows, with no duplicate prompts; 800 is a hard limit. About 500 rows is a good target that should yield good results, and try to generate no fewer than 200 examples. The default RL recipe draws {RL_PROMPT_DRAWS} prompts and samples 8 completions per prompt ({RL_COMPLETIONS} completions total). Prompts are drawn repeatedly from the training partition; a small dataset is revisited more often. You may revise your data and run RL as often as your time and quotas allow.

Your model will be tested on a public benchmark of expert-written algorithmic problems, the same one the validation tasks come from. Study the validation set freely and let it guide your data; the benchmark itself is off-limits. Do not search for, download, or browse it. Do not train on its problems (or ones you suspect are in it), their solutions (including published model solutions), or edited versions of them, and do not try to reconstruct it or work out which problems it contains. General public material such as tutorials, algorithm references, and documentation is fine and encouraged. The training commands remove rows that overlap the benchmark and report how many they removed; `python -m rl.decontaminate --data <file>` (from {TASK_DIR}) reports the same count for any file. Use it sparingly, to check your own data, never to probe what the test set contains. Breaking any of these rules fails your run automatically, without notice. The goal is a model that is genuinely strong at this kind of problem, not one that has memorized the benchmark.

Each prompt must fit in {MAX_SFT_LENGTH} tokens; longer rows are rejected, not truncated. The harness holds out a fixed 10% of your rows to monitor RL reward and trains on the rest; do not generate a separate evaluation set.

Check the format before training and again after your last edit (from {TASK_DIR}):
python -m rl.agent_training validate --data {RAW_DATA_PATH}
This checks the schema, weights, thinking targets, grade() signatures, and RestrictedPython compilation. It does not run criteria or call the judge. It prints the row count.

# LLM API Usage

Generation has a shared quota of {GENERATION_TOKEN_UNIT_LIMIT} token units. DeepSeek-V4-Flash costs 1 unit per input token and 3 units per output token; GLM-5.3 costs 4 units per input token and 12.5 units per output token. Count cached inputs at full weight and include reasoning in output tokens. Use `litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731` or `litellm_proxy/azure_ai/FW-GLM-5.3`; other model families have no defined unit weights for this run.

Read `{GENERATION_USAGE_PATH}` for cumulative `token_units`, `remaining_token_units`, and `cost_usd`. `unpriced_calls` counts responses without dollar pricing; only token units enforce the quota. The quota spans all pipeline iterations and processes. Each call holds its worst case in the shared ledger while it is in flight (its prompt plus `max_tokens` for every completion, or 65,536 tokens per completion without `max_tokens`), and new calls stop once used plus held units reach the quota. A response replaces its hold with its actual usage. A call that times out, loses its connection, or is still running when its process is killed stays charged at its full hold, because the API may still bill it; the ledger counts these in `unreturned_calls` (a killed process's holds move there after two hours). Setting `max_tokens` keeps holds close to real usage. Do not delete/reset the ledger or change its environment settings. The OpenHands model driving your agent turns is accounted separately.

Credentials are provided as `LITELLM_API_KEY` and `LITELLM_BASE_URL`; load them from the environment without printing them. Forger's Model records usage against this quota automatically, so make your generation calls through Forger and do not wrap Model calls a second time.

DeepSeek-V4-Flash returns its reasoning separately from its answer, and Forger keeps it: `sample_from_LLM` and `generate_from_context` put it under each output's `thinking_trace` key. Set the effort explicitly, e.g. `Model(..., reasoning_effort="high")`: without it DeepSeek-V4-Flash does not think at all, and the setting controls how long the reasoning is.
