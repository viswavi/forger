# Task: Open-Ended Algorithmic Programming

You must generate a training dataset to help models like yourself improve at open-ended algorithmic programming. You will do this by generating prompts and rubrics. You will perform RL using your prompts and rubrics, then submit the final RL checkpoint you choose.

In this setup, a model is given a problem statement and must answer, in a single response with no tools and no feedback, with one self-contained C++17 program. Most problems have no single correct output: they are optimization, construction, or interactive problems, and an answer earns partial credit for how good it is. The statement gives the input and output format and how an answer is scored. Each problem has one time limit and one memory limit for all its tests, enforced as in the benchmark: the time limit is CPU time per test (a run is also killed at twice it in wall-clock time), the memory limit caps address space and stack (peak resident memory in interactive problems), and compilation gets 10 seconds of CPU. Every task_text ends with the enforced values, which validation rows also carry as "time_limit_s" and "memory_mb"; the statement above them may omit them or state different ones. The program is compiled with `g++ -O2 -std=gnu++17` and run on every test of the problem, with the test's input on stdin. In an interactive problem, the program instead talks to an interactor program over stdin and stdout, so it must flush its output after every message. A checker or interactor then scores each test between 0 and 1: matching a strong reference answer is worth 0.6, beating it is worth more on a logarithmic scale (capped at 1), and weaker answers earn less, down to 0. A test scores 0 when the program does not compile, exceeds the time or memory limit, crashes, or produces an invalid answer. An answer's score is the mean over its tests, times 100; a problem's score is the mean over 4 independently sampled answers, and performance is the mean problem score.

Every test counts equally, so an answer that is valid and reasonable on every test can outscore one that is excellent on some tests but invalid, too slow, or crashing on others. Your data should make the model's programs better: reading the statement and its scoring rule carefully, producing valid output every time, staying within the limits, and finding better solutions with good algorithms and heuristics.

Public validation examples are shown in {TASK_DIR}/validation_tasks.jsonl -- use these however you like. They can be useful for imitating the data distribution, if you want to; but training on validation tasks leaves the validation set substantially degraded for choosing checkpoints. Each contains the following keys: ["id", "type", "n_tests", "time_limit_s", "memory_mb", "statement", "task_text"]. "type" is "interactive" or "default", and "n_tests" is the number of tests the problem is judged on. Each validation problem's judging files are in {TASK_DIR}/problems/<id>/: config.yaml (time and memory limits), testdata/ (every test's input and answer file), and the source of its checker (chk.cc) or interactor (interactor.cc), written with testlib.h ({TASK_DIR}/testlib/testlib.h). If compatible baseline outputs are available, you will also find model output files {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/metrics.json (summary metrics) and {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/predictions.jsonl (per-row predictions on the validation set; each row's "samples" holds its 4 sampled answers, and each answer's "cases" lists every test with its file in testdata/, status, score, and the start of the checker's or interactor's message). Feel free to use these predictions/summary metrics to inform your data generation approach.

"task_text" (and the "question" field in model_outputs/{BASELINE_MODEL}/val/predictions.jsonl) is the exact user-turn prompt text shown to a candidate model at evaluation time: "Problem:", a blank line, the statement, a blank line, a "Judging limits ..." line giving the problem's enforced time and memory limits and the compiler, a blank line, and "Generate solution code:". A system message, separate from task_text (`SYSTEM_PROMPT` in {TASK_DIR}/prompt_building.py), asks for a C++ solution that respects the stated limits, wrapped in a ```cpp fence, with no other text. The evaluator takes the longest ```cpp block in the text after the final </think>; a response with no code scores 0. Your submitted prompts are used verbatim for training, so build them the same way: `prompt_building.build_user_content(statement, time_limit_s, memory_mb)` gives the task_text, and `prompt_building.build_candidate_prompt(task_text)` the system message followed by the user turn. Training on any other prompt format will not transfer to evaluation.

# Data Format

Write ONE dataset to {RAW_DATA_PATH} (write a temporary file, then rename it). Each JSONL row has the fields "prompt" and "rubric", and optionally "ground_truth":
{{"prompt": [{{"role": "system", "content": "..."}}, {{"role": "user", "content": "..."}}], "ground_truth": "a reference answer (optional)", "rubric": [[{{"code": "def grade(prompt, response, ground_truth):\n    return 1.0"}}, 1.0], [{{"prompt": "Describe a criterion for the judge"}}, 1.0]]}}
The constant score above only illustrates syntax; use meaningful criteria.

- "prompt" is the chat messages, ending in a user turn. RL samples responses to these messages; neither the ground truth nor the rubric is ever shown to the policy.
- "ground_truth" is optional text that your criteria receive, for example a reference answer (one complete C++17 program in a ```cpp fence); it is "" when omitted. Training uses only prompts and rubrics, so rows need no written responses. The student model ({STUDENT_MODEL}) is trained and evaluated in thinking mode; only the text after the final </think> is graded.
- "rubric" is a nonempty list of [criterion, weight] pairs with finite, nonnegative weights and a positive sum. The RL reward is the weighted mean of the criterion scores. Each criterion is either:
  - {{"code": ...}}: Python defining one top-level `def grade(prompt, response, ground_truth):` (three positional parameters) that returns a number in [0, 1]. `prompt` is the chat messages; `response` includes its thinking trace. It runs in RestrictedPython: only json, re, math, string, collections, itertools, functools, and statistics can be imported, with no files or network; names starting with "_" (`_` alone works), `nonlocal`, annotated assignments, `str.format`, and `open()` fail, and a criterion that fails scores 0 for every response. grade() can call `judge_cpp(code, tests, checker=None, interactor=None, time_limit=1.0, memory_mb=256, details=False)`, which compiles and judges a C++ program as the evaluator does. `tests` is a list of {{"input": stdin, "answer": answer file, "args": [command-line arguments]}} ("answer" and "args" are optional; without "answer", a clean run passes). `checker` or `interactor` is testlib C++ source (with neither, the output must equal the answer up to whitespace) that scores a test by exiting with `quitf(_ok, ...)` (1), `quitp(x, ...)` printing `Ratio: <x>` (x), or `quitf(_wa, ...)` (0). It returns (mean score, per-test statuses), or with `details=True` (mean score, one {{"status", "ratio", "time", "stdout", "message"}} dict per test). Each criterion gets 20 seconds in total, compilation included, and runs on every sampled RL response, so use a few small, fast tests. From {TASK_DIR}: `from rl.rubric_sandbox import Sandbox` gives `Sandbox().judge_cpp(...)`; `python rl/rubric_worker.py < criterion.json` (a JSON object with "code", "prompt", "response", and "ground_truth") prints the score RL would give; and `from rl.solution_runner import score_targets` scores each row's ground_truth with its own code criteria (`score_targets(rows)`), so a target that scores lower than you expect has a rubric, checker, or program that fails in RL.
  - {{"prompt": ...}}: a natural-language criterion. The judge model (DeepSeek-V4-Flash) scores it given the criterion, the prompt, the full response, and the ground truth. With {{"prompt": ..., "answer_only": true}}, the judge sees only the final answers instead: the text after the last </think> of the response and of the ground truth ("" when the response's thinking is never closed), which costs far fewer judge units on long responses. For this task, code criteria are usually the better choice: a program's validity and the quality of its answers can be measured exactly, while prompted criteria use judge quota and make the RL reward noisier.

Submit at least 10 and at most 800 rows, with no duplicate prompts; 800 is a hard limit. About 500 rows is a good target that should yield good results, and try to generate no fewer than 200 examples. The default RL recipe draws {RL_PROMPT_DRAWS} prompts and samples 8 completions per prompt ({RL_COMPLETIONS} completions total). Prompts are drawn repeatedly from the training partition; a small dataset is revisited more often. You may revise your data and run RL as often as your time and quotas allow. Prompts whose completions all get the same reward provide no within-group RL signal.

Your trained models will be evaluated against a publicly available benchmark of algorithmic problems designed and written by hand by experts, which the validation tasks are also drawn from. Use the validation set freely and let it guide your decisions: study its problems, the kinds of tasks, formats, scoring rules and difficulty it contains, and where the baseline model fails on it, and shape your data accordingly. What is off-limits is the benchmark itself: do not download or browse it, do not train on problems you think might be in the test set, their solutions (including published model solutions) or edited versions of them, and do not try to rebuild or reverse-engineer the benchmark, its specific problems or the way they were constructed, item by item. General material from the web and other public sources (tutorials, algorithm references, documentation) is fine and encouraged to use; only the benchmark itself, its problems and their solutions are off-limits, including searching for them. The training commands remove rows that overlap with it before training and report how many they removed. You may use the decontamination script sparingly to make sure you are not cheating, but do not exploit these training commands to try to reverse-engineer or confirm the composition of the test set. Any of this behavior will cause an automatic failure of your run without notification. Your goal is a model that is genuinely strong on this kind of problem, not one that has memorized the benchmark. The decontamination script reports how many rows of a file overlap: python -m rl.decontaminate --data <file> (run from {TASK_DIR}).

Each prompt must fit in {MAX_SFT_LENGTH} tokens; longer rows are rejected, not truncated. The harness holds out a fixed 10% of your rows to monitor RL reward and trains on the rest; do not generate a separate evaluation set.

Check the format before training and again after your last edit (from {TASK_DIR}):
python -m rl.agent_training validate --data {RAW_DATA_PATH}
This checks the schema, weights, thinking targets, grade() signatures, and RestrictedPython compilation. It does not run criteria or call the judge. It prints the row count.

# LLM API Usage

Generation has a shared quota of {GENERATION_TOKEN_UNIT_LIMIT} token units. DeepSeek-V4-Flash costs 1 unit per input token and 3 units per output token; GLM-5.3 costs 4 units per input token and 12.5 units per output token. Count cached inputs at full weight and include reasoning in output tokens. Use `litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731` or `litellm_proxy/azure_ai/FW-GLM-5.3`; other model families have no defined unit weights for this run.

Read `{GENERATION_USAGE_PATH}` for cumulative `token_units`, `remaining_token_units`, and `cost_usd`. `unpriced_calls` counts responses without dollar pricing; only token units enforce the quota. The quota spans all pipeline iterations and processes. Each call holds its worst case in the shared ledger while it is in flight (its prompt plus `max_tokens` for every completion, or 65,536 tokens per completion without `max_tokens`), and new calls stop once used plus held units reach the quota. A response replaces its hold with its actual usage. A call that times out, loses its connection, or is still running when its process is killed stays charged at its full hold, because the API may still bill it; the ledger counts these in `unreturned_calls` (a killed process's holds move there after two hours). Setting `max_tokens` keeps holds close to real usage. Do not delete/reset the ledger or change its environment settings. The OpenHands model driving your agent turns is accounted separately.

Credentials are provided as `LITELLM_API_KEY` and `LITELLM_BASE_URL`; load them from the environment without printing them. Use the public accounting helpers below for every API call, instead of calling LiteLLM directly. These standalone helpers are permitted in this baseline and do not require importing the Forger library. Each helper call makes one attempt (pass no `num_retries`); retry failed calls in your own code.

```python
import os
import sys
sys.path.insert(0, "{TASK_DIR}")
from rl.token_budget import completion  # acompletion is available for async calls

response = completion(
    model="litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731",
    messages=[{{"role": "user", "content": "What is 273 * 149?"}}],
    api_key=os.environ["LITELLM_API_KEY"],
    api_base=os.environ["LITELLM_BASE_URL"],
    temperature=1.0,
    reasoning={{"effort": "low"}},
    n=1,
)
```

DeepSeek-V4-Flash returns its reasoning separately from its answer, in `response.choices[0].message.reasoning_content`. Use it for <think>...</think> targets instead of making another call to write reasoning. DeepSeek-V4-Flash reads the effort only as `reasoning={{"effort": ...}}` and does not think at all without it; GLM-5.3 reads `reasoning_effort="low"` (or "medium", "high") instead. The setting controls how long the reasoning is.

# High-Level Approach

You are encouraged to run things and iterate on the data you receive in writing your pipeline. Put all your data in {AGENT_DATA_DIR}/. You can write your pipeline as {AGENT_DATA_DIR}/pipeline_{{1,2,3,4,...}}.py. Each time you make a set of changes, even if minor, you can copy the old script directly (e.g. cp pipe1.py pipe2.py) before editing the new copy, so the trajectory of changes is tracked as you iterate. It is strongly encouraged to make multiple iterations over your dataset, in this way -- you should make _at minimum_ write and execute 2 or 3 small-scale iterations of your data pipeline (each saved as pipeline_{{1,2,3}}.py) (and as many as 20 or 30 iterations total or more) before launching your large-scale run.

Get a small end-to-end loop working early. After that, test out different decisions -- data sources, refinement operations, and filters. Feel free to generate a few dozen rows, validate them, run an RL probe on them, and evaluate a checkpoint on validation at any point. Then scale up and refine. A working loop shows you what actually needs fixing, and leaves you with a valid submission to improve on.

Check data quality directly at every stage, before training on it: read samples, and look at the distributions of rubric scores, lengths, difficulty, and diversity. A training run plus evaluation takes hours and folds many causes into one number, so use it as the final check of data you have already validated, not as the way to find out whether data is good.
