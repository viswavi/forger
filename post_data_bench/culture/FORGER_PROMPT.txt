# Task: Cultural Norm Reasoning

You must generate a training dataset to help models like yourself improve at cultural commonsense reasoning. You will do this by generating prompts and rubrics. You will perform RL using your prompts and rubrics, then submit the final RL checkpoint you choose.

In this setup, a model is given a country and a short everyday scenario and must judge whether the characters' behavior is appropriate given the cultural and social norms of that country. The answer is "yes" if the behavior aligns with known cultural norms there, "no" if it violates an established norm there, or "neutral" if the scenario neither specifically adheres to nor specifically violates any norm particular to that country. Models are currently fairly good at identifying "yes" and "no" cases; our goal is to maintain or improve their precision on those while significantly improving their ability to identify "neutral" cases.

Both goals matter. Performance is measured by macro-F1 over the three labels, so each label counts equally: a model that answers "neutral" more often but loses precision on "yes" and "no" can score worse overall. Your data should make the model's judgments better (knowing the norms of many countries, reading the scenario carefully, telling a norm particular to the country from behavior that is ordinary or merely polite everywhere), not only shift it toward one label.

Public validation examples are shown in {TASK_DIR}/validation_tasks_de_obfuscated.jsonl -- use these however you like. They can be useful for imitating the data distribution, if you want to; but training on validation tasks leaves the validation set substantially degraded for choosing checkpoints. Each contains the following keys: ["id", "country", "axis", "subaxis", "value", "rule_of_thumb", "situation", "task_text", "gold_label"]. "gold_label" is the correct answer; "axis", "subaxis", "value" and "rule_of_thumb" describe the norm the scenario was written about, and are not shown to the model. If compatible baseline outputs are available, you will also find model output files {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/metrics.json (summary metrics) and {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/predictions.jsonl (per-row predictions on the validation set). Feel free to use these predictions/summary metrics to inform your data generation approach.

"task_text" (and the "question" field in model_outputs/{BASELINE_MODEL}/val/predictions.jsonl) is the exact user-turn prompt text shown to a candidate model at evaluation time: "Country: <country>" on one line, then "Situation: <scenario>". A system message, separate from task_text (`SYSTEM_PROMPT` in {TASK_DIR}/prompt_building.py), defines the three labels and asks the model to conclude with "Answer: yes", "Answer: no", or "Answer: neutral". The evaluator reads the label after the last "Answer:" in the text after the final </think>; any other ending scores as wrong. Your submitted prompts are used verbatim for training, so build them the same way: `prompt_building.build_candidate_prompt(task_text)` gives the system message followed by the user turn. Training on any other prompt format will not transfer to evaluation.

# Data Format

Write ONE dataset to {RAW_DATA_PATH} (write a temporary file, then rename it). Each JSONL row has the fields "prompt" and "rubric", and optionally "ground_truth":
{{"prompt": [{{"role": "system", "content": "..."}}, {{"role": "user", "content": "..."}}], "ground_truth": "a reference answer (optional)", "rubric": [[{{"code": "def grade(prompt, response, ground_truth):\n    return 1.0"}}, 1.0], [{{"prompt": "Describe a criterion for the judge"}}, 1.0]]}}
The constant score above only illustrates syntax; use meaningful criteria.

- "prompt" is the chat messages, ending in a user turn. RL samples responses to these messages; neither the ground truth nor the rubric is ever shown to the policy.
- "ground_truth" is optional text that your criteria receive, for example the reference label ("Answer: yes", "Answer: no", or "Answer: neutral"); it is "" when omitted. Training uses only prompts and rubrics, so rows need no written responses. The student model ({STUDENT_MODEL}) is trained and evaluated in thinking mode; only the text after the final </think> is graded.
- "rubric" is a nonempty list of [criterion, weight] pairs with finite, nonnegative weights and a positive sum. The RL reward is the weighted mean of the criterion scores. Each criterion is either:
  - {{"code": ...}}: Python defining exactly one top-level synchronous function `def grade(prompt, response, ground_truth):` with exactly three positional parameters (no decorators, *args, **kwargs, or keyword-only parameters). `prompt` is the list of chat messages; `response` and `ground_truth` are strings; `response` includes its thinking trace. Return a finite number in [0, 1] (not a boolean). Code runs in RestrictedPython with only json, re, math, string, collections, itertools, functools, and statistics importable, and no files or network. The sandbox refuses some ordinary Python: names and attributes starting with "_" (`def _helper`, `self._x`, reading `__name__`), `nonlocal`, and annotated assignments such as `x: int = 0` do not compile, and `str.format`, `str.format_map`, and `open()` fail when called. `_` alone (`for _ in range(t)`), f-strings, `%` formatting, and the `format()` builtin work. A criterion that uses a refused construct scores 0 for every response, so check your criteria in this sandbox before relying on them. From {TASK_DIR}, `python rl/rubric_worker.py < criterion.json` scores one criterion exactly as RL does, given a JSON object with "code", "prompt", "response", and "ground_truth", and prints {{"score": ...}} or {{"error": ..., "message": ...}}. To check many at once, `from rl.solution_runner import score_targets` uses the same sandbox and limits in parallel worker processes: `score_targets(rows)` scores each row's ground_truth with the row's own code criteria exactly as an RL reward would. Run score_targets on your final dataset: a correct target that scores below 1 has a rubric that fails in RL. Each criterion gets 20 seconds in total; errors and timeouts in grade() score 0.
  - {{"prompt": ...}}: a natural-language criterion. The judge model (DeepSeek-V4-Flash) scores it given the criterion, the prompt, the full response, and the ground truth. With {{"prompt": ..., "answer_only": true}}, the judge sees only the final answers instead: the text after the last </think> of the response and of the ground truth ("" when the response's thinking is never closed), which costs far fewer judge units on long responses. The final label can be checked exactly with code; prompted criteria use judge quota and make the RL reward noisier.

Submit at least 10 and at most 2,000 rows, with no duplicate prompts; 2,000 is a hard limit. About 1,250 rows is a good target: get as close to it as your quota and time allow, and realistically aim for at least 800. The default RL recipe draws {RL_PROMPT_DRAWS} prompts and samples 8 completions per prompt ({RL_COMPLETIONS} completions total). Prompts are drawn repeatedly from the training partition; a small dataset is revisited more often. You may revise your data and run RL as often as your time and quotas allow. Prompts whose completions all get the same reward provide no within-group RL signal.

Your trained models will be evaluated against a well-known public dataset of cultural-norm scenarios, which the validation tasks are also drawn from. Use the validation set freely and let it guide your decisions: study its scenarios, the countries and kinds of norms it covers, its label balance, and where the baseline model fails on it, and shape your data accordingly. What is off-limits is the dataset itself: do not download or browse it, do not train on scenarios you think might be in the test set or edited versions of them, and do not try to rebuild or reverse-engineer the dataset, its specific scenarios or the way they were constructed, item by item. The training commands remove rows that overlap with it before training and report how many they removed. You may use the decontamination script sparingly to make sure you are not cheating, but do not exploit these training commands to try to reverse-engineer or confirm the composition of the test set. Any of this behavior will cause an automatic failure of your run without notification. Your goal is a model that genuinely reasons well about cultural norms, including recognizing when no norm particular to the country applies, not one that has memorized the benchmark. The decontamination script reports how many rows of a file overlap: python -m rl.decontaminate --data <file> (run from {TASK_DIR}).

Each prompt must fit in {MAX_SFT_LENGTH} tokens; longer rows are rejected, not truncated. The harness holds out a fixed 10% of your rows to monitor RL reward and trains on the rest; do not generate a separate evaluation set.

Check the format before training and again after your last edit (from {TASK_DIR}):
python -m rl.agent_training validate --data {RAW_DATA_PATH}
This checks the schema, weights, thinking targets, grade() signatures, and RestrictedPython compilation. It does not run criteria or call the judge. It prints the row count.

# LLM API Usage

Generation has a shared quota of {GENERATION_TOKEN_UNIT_LIMIT} token units. DeepSeek-V4-Flash costs 1 unit per input token and 3 units per output token; GLM-5.3 costs 4 units per input token and 12.5 units per output token. Count cached inputs at full weight and include reasoning in output tokens. Use `litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731` or `litellm_proxy/azure_ai/FW-GLM-5.3`; other model families have no defined unit weights for this run.

Read `{GENERATION_USAGE_PATH}` for cumulative `token_units`, `remaining_token_units`, and `cost_usd`. `unpriced_calls` counts responses without dollar pricing; only token units enforce the quota. The quota spans all pipeline iterations and processes. Each call holds its worst case in the shared ledger while it is in flight (its prompt plus `max_tokens` for every completion, or 65,536 tokens per completion without `max_tokens`), and new calls stop once used plus held units reach the quota. A response replaces its hold with its actual usage. A call that times out, loses its connection, or is still running when its process is killed stays charged at its full hold, because the API may still bill it; the ledger counts these in `unreturned_calls` (a killed process's holds move there after two hours). Setting `max_tokens` keeps holds close to real usage. Do not delete/reset the ledger or change its environment settings. The OpenHands model driving your agent turns is accounted separately.

Credentials are provided as `LITELLM_API_KEY` and `LITELLM_BASE_URL`; load them from the environment without printing them. Forger's Model records usage against this quota automatically, so make your generation calls through Forger and do not wrap Model calls a second time.

DeepSeek-V4-Flash returns its reasoning separately from its answer, and Forger keeps it: `sample_from_LLM` and `generate_from_context` put it under each output's `thinking_trace` key. Use it for <think>...</think> targets instead of making another call to write reasoning. Set the effort explicitly, e.g. `Model(..., reasoning_effort="high")`: without it DeepSeek-V4-Flash does not think at all, and the setting controls how long the reasoning is.
