# Task: Code Generation

You must generate a training dataset to help models like yourself improve at the task of code generation. Specifically,  our goal is to maintain or improve models' ability to generate working code when possible while avoiding generating code for tasks that are literally impossible to solve. You will do this by generating prompts, responses, and rubrics. The prompts and responses will finetune a base model (to instill good "behaviors" to the model), and then we will perform RL on this finetuned checkpoint using the prompts and rubrics (to maximize the effectiveness of the model).

In this code generation setup, a user provides a problem description to a model along with public test cases (input-output pairs) that must be passed in order for the solution to be correct. The user will secretly have private test cases, not shown to the model, and if the model generates a solution that passes all of the user's public and private test cases, then the model has succeeded. The model must produce a self-contained snippet of Python code (including imports if necessary, e.g. standard-library modules like sys or common libraries like numpy). Sometimes a user will provide test cases that are intractable or impossible to pass (e.g. the problem is indeterminate, ill-posed, or undecidable/uncomputable, or there is no solution that matches the user's problem description but also passes the provided test cases). In this case, the model should simply return "This task is impossible to complete given the provided tests." instead of returning any code. Currently, models struggle at determining whether a task is impossible; we wish to improve at this ability, while also improving at generating functional code when applicable.

Both goals matter. Abstaining correctly on impossible tasks is important, but improving the solve rate on solvable tasks is just as important and must not get lost: most evaluation tasks are solvable, so a model that abstains more but solves fewer solvable tasks can score worse overall. Your data should make the model's code better (correct algorithms, edge cases, efficiency, careful reading of the statement and tests), not only teach it when to abstain, and it must not teach the model to abstain on tasks it could solve.

Public validation examples are shown in {TASK_DIR}/validation_tasks_de_obfuscated.jsonl -- use these however you like. They can be useful for imitating the data distribution, if you want to; but training on validation tasks leaves the validation set substantially degraded for choosing checkpoints. Each contains the following keys: ["question_content", "starter_code", "public_test_cases", "gold_response", "question_title", "contest_date", "contest_id", "difficulty", "metadata", "platform", "private_test_case_idx", "question_id", "task_text"]. If compatible baseline outputs are available, you will also find model output files {TASK_DIR}/model_outputs/Qwen__Qwen3-8B_tinker/val/metrics.json (summary metrics) and {TASK_DIR}/model_outputs/Qwen__Qwen3-8B_tinker/val/predictions.jsonl (per-row predictions on the validation set). Feel free to use these predictions/summary metrics to inform your data generation approach.

"task_text" (and the "question" field in model_outputs/Qwen__Qwen3-8B_tinker/val/predictions.jsonl) is the exact user-turn prompt text shown to a candidate model at evaluation time: a "### Question:" section (the raw question_content), a "### Format:" section (starter-code instructions plus the starter code block when starter_code is non-empty, otherwise generic stdin/stdout instructions), a "### Public Test Cases" section (each test case rendered as "Input:"/"Output:" lines), and a final "### Answer:" prompt. A system message, separate from task_text, identifies the model as an expert Python programmer and adds the instruction to respond with exactly "This task is impossible to complete given the provided tests." when genuinely convinced a task is unsolvable. Your submitted prompts are used verbatim for training, so build them the same way: the system message (`SYSTEM_MESSAGE + ABSTENTION_INSTRUCTION` in {TASK_DIR}/prompt_building.py) followed by a user turn in the task_text format above. Training on any other prompt format will not transfer to evaluation.

# Data Format

Write ONE dataset to {RAW_DATA_PATH} (write a temporary file, then rename it). Each JSONL row has exactly three fields, "prompt", "ground_truth", and "rubric":
{{"prompt": [{{"role": "system", "content": "..."}}, {{"role": "user", "content": "..."}}], "ground_truth": "<think>reasoning</think>final answer", "rubric": [[{{"code": "def grade(prompt, response, ground_truth):\n    return 1.0"}}, 1.0], [{{"prompt": "Describe a criterion for the judge"}}, 1.0]]}}
The constant score above only illustrates syntax; use meaningful criteria.

- "prompt" is the chat messages, ending in a user turn. The same messages are used for SFT and RL; neither the target nor the rubric is ever shown to the policy.
- "ground_truth" is the complete SFT target: a nonempty thinking trace inside <think>...</think>, then the final answer (a solution in a ```python fence, or exactly "This task is impossible to complete given the provided tests."). Targets need long-form thinking traces well-suited to the student model ({STUDENT_MODEL}), which is trained and evaluated in thinking mode; only the text after the final </think> is graded.
- "rubric" is a nonempty list of [criterion, weight] pairs with finite weights whose positive weights have a positive sum. The RL reward is (sum of weight x criterion score) / (sum of the positive weights), clipped to [0, 1], so a criterion with a negative weight lowers the reward when the response does what it describes, e.g. [{{"prompt": "States a wrong final answer"}}, -2]. The judge never sees weights: it judges whether the response does what the criterion describes. Each criterion is either:
  - {{"code": ...}}: Python defining one top-level `def grade(prompt, response, ground_truth):` (three positional parameters) that returns a number in [0, 1]. `prompt` is the chat messages; `response` and `ground_truth` include their thinking traces. It runs in RestrictedPython: only json, re, math, string, collections, itertools, functools, and statistics can be imported, with no files or network. To test a response's code, grade() can call `run_program(code, stdin)`, which returns (True, stdout) or (False, error type), and `call_method(code, class_name, method_name, *args)`, which returns (True, result) or (False, error type) with results JSON-normalized (tuples become lists); that code runs in its own sandbox with common competitive-programming imports (sys, heapq, bisect, collections, itertools, math, numpy, ...) and 4 seconds per run. grade() can also call `judge_cpp(code, tests, checker=None, interactor=None, time_limit=1.0, memory_mb=256, details=False)`, which compiles a C++ program with `g++ -O2 -std=gnu++17` and judges it on `tests`, a list of {{"input": stdin, "answer": answer file, "args": [command-line arguments]}} ("answer" and "args" are optional; without "answer", a clean run passes), with `checker` or `interactor` as testlib C++ source (with neither, the output must equal the answer up to whitespace); it returns (mean score, per-test statuses), or with `details=True` (mean score, one {{"status", "ratio", "time", "stdout", "message"}} dict per test). grade() can also call `final_answer(response)`, the text after the last `</think>` ("" while a `<think>` is still open); call it rather than writing the tags, which the LLM gateway can rewrite in model-written code. Both sandboxes refuse names and attributes starting with "_" (`__slots__`, `self._x`, `def _helper`; `_` alone and dunder methods such as `__init__` work), `nonlocal`, annotated assignments (so @dataclass fields), `str.format`, and `open()`; `run_program` strips an `if __name__ == "__main__":` guard but `call_method` does not. A correct answer that uses a refused construct scores 0, so check gold answers and targets in this sandbox. From {TASK_DIR}: `from rl.rubric_sandbox import Sandbox` gives `Sandbox().run_program(code, stdin=...)`, `.call_method(...)`, and `.judge_cpp(...)`; `python rl/rubric_worker.py < criterion.json` (a JSON object with "code", "prompt", "response", and "ground_truth") prints the score RL would give; and `from rl.solution_runner import run_solution, score_targets` gives `run_solution(code, tests)`, which runs a solution on tests ({{"input": stdin, "output": expected}}, or {{"call": [class_name, method_name, arg, ...], "output": expected}}) and says why a refused construct failed, and `score_targets(rows)`, which scores each row's ground_truth with its own code criteria, so a correct target that scores below 1 has a rubric or code that fails in RL. Each criterion gets 20 seconds in total; errors and timeouts score 0. Every test runs on every sampled RL response, so use a handful of small tests that separate correct from incorrect solutions.
  - {{"prompt": ...}}: a natural-language criterion. The judge model (DeepSeek-V4-Flash) scores it given the criterion, the prompt, the full response, and the ground truth. With {{"prompt": ..., "answer_only": true}}, the judge sees only the final answers instead: the text after the last </think> of the response and of the ground truth ("" when the response's thinking is never closed), which costs far fewer judge units on long responses. Two more options shape what the judge gets: "judge_sees" lists which of "prompt", "response" and "ground_truth" it receives (it must include "response"; all three by default), so {{"prompt": ..., "judge_sees": ["response"]}} sends neither the chat nor the ground truth; and "instructions" is text of up to 4,000 characters added to the judge's system message for that criterion only. "scale" sets how the judge answers: "binary" (the default) asks yes or no, scored 1 or 0, and "likert" asks an integer from 1 (not at all) to 5 (fully), scored 0, 0.25, 0.5, 0.75 or 1; instructions cannot change the scale. Code criteria may return any value in [0, 1]. For this task, code criteria are usually the better choice: correctness and abstention can be checked exactly, while prompted criteria use judge quota and make the RL reward noisier. When the provider's content filter blocks the judge's reply, that criterion is ungraded and RL does not train on that response (e.g. a sampled answer that goes along with an unsafe request).

Submit at least 10 and at most 2,000 rows, with no duplicate prompts; 2,000 is a hard limit. About 1,600 rows is a good target: get as close to it as your quota and time allow, and realistically aim for at least 800. The final RL run draws 25 x 128 = 3,200 prompts from your training rows, so 1,600 rows gives each prompt about two RL steps, a setting that has been tested. With few rows, RL revisits the same prompts many times (about 12 times at 300 rows). Because SFT trains on the same rows, the checkpoint has already seen a target for every RL prompt, and prompts it always solves give RL no signal.

Each prompt plus target must fit in {MAX_SFT_LENGTH} tokens; longer rows are rejected, not truncated, so avoid overly long thinking traces. The harness holds out a fixed 10% of your rows to monitor RL reward and uses the rest for both SFT and RL; do not generate a separate evaluation set.

Check the format before training and again after your last edit (from {TASK_DIR}):
python -m rl.agent_training validate --data {RAW_DATA_PATH}
This checks the schema, weights, thinking targets, grade() signatures, and RestrictedPython compilation. It does not run criteria or call the judge. It prints the row count.

# Training and Validation

Your sandbox has {GPU_DESCRIPTION}. Do not train or serve LLMs on it. SFT, RL probes, and all sampling of the student model run on Tinker (remote LoRA training of {STUDENT_MODEL}). Train, validate, and probe with these commands, run from {TASK_DIR}:

- SFT trial (use a new output directory per trial):
  python -m rl.agent_training sft --data {RAW_DATA_PATH} --output-dir {AGENT_DATA_DIR}/sft_trial_1
  Optional: --epochs (default 4), --lr (default 1e-6, a full-finetune learning rate; the LoRA trainer multiplies it by 10 automatically), --lora-rank (default 32), --batch-size (default 128). The trial directory records its weights in tinker_checkpoint.json; "sampler_path" is the model to evaluate.
- Validation evaluation (same evaluator and settings as the final evaluation):
  bash {TASK_DIR}/evaluate_model.sh --split val --server-backend tinker --model-path <sampler_path> --out-dir {AGENT_DATA_DIR}/validation/sft_trial_1
  Read metrics.json and predictions.jsonl in the output directory. Use a fresh output directory whenever the weights or settings change, because the evaluator resumes existing outputs. --model-path {STUDENT_MODEL} evaluates the base model.
- Short RL probe (2 small steps of the final RL recipe, 16 prompts x 8 samples each):
  python -m rl.agent_training probe --data {RAW_DATA_PATH} --checkpoint {AGENT_DATA_DIR}/sft_trial_1 --output-dir {AGENT_DATA_DIR}/rl_probe_1
  It writes train_log.jsonl (reward, truncated fraction, groups whose samples got different rewards), heldout_log.jsonl, and rollouts.jsonl: per prompt, its rewards, which samples hit the length limit or had a judged criterion blocked by the content filter, and the start of each final answer, keyed by `prompt_id` (`rl.rubric_data.prompt_id(row)` gives it for your rows). From it you can count, for example, how often the policy abstains on your impossible rows and on your solvable ones.

The final model is your SFT checkpoint after RL, and RL is where most of the improvement comes from. SFT alone often moves validation accuracy little, and may even lower it: its job is to plant behaviors (abstaining, a solution format, a style of reasoning) that RL then amplifies or removes, depending on your rubrics and on which RL prompts get a reward signal. Spend your effort accordingly: the rubrics and RL prompts matter at least as much as the SFT targets. Validation accuracy right after SFT is therefore a weak signal for choosing between datasets, rubrics, or checkpoints. Before submitting, probe your final dataset and checkpoint, which shows what RL will start from, and read its rollouts: rewards should vary within groups, few samples should be truncated, and the policy should abstain on impossible rows without abstaining on solvable ones. Probes spend the final RL budget, so run a few, not dozens.

RL learns only from prompts whose samples get different rewards: a prompt your checkpoint always solves, or always fails, gives it no signal. Before submitting, measure how often your SFT checkpoint already solves your rows. `from rl.solution_runner import rubric_verifier, rubric_score` gives `rubric_verifier(threshold=1.0)`, which grades one sampled response with its row's rubric as the RL reward does (code criteria only, on the whole response, thinking included) and returns True when the reward reaches `threshold`, and `rubric_score()`, which returns the reward itself. Both run only code criteria; `rubric_score(judge=True)` also scores prompt criteria with the RL judge (charged to the judge quota) and returns the full RL reward.

After your session ends, the host runs a fixed RL recipe on your rubrics, starting from your submitted SFT checkpoint, and then evaluates on the secret test set. This happens outside your time budget.

# High-Level Approach

You are encouraged to run things and iterate on the data you receive in writing your pipeline. Put all your data in {AGENT_DATA_DIR}/. You can write your pipeline as {AGENT_DATA_DIR}/pipeline_{{1,2,3,4,...}}.py. Each time you make a set of changes, even if minor, you can copy the old script directly (e.g. cp pipe1.py pipe2.py) before editing the new copy, so the trajectory of changes is tracked as you iterate. It is strongly encouraged to make multiple iterations over your dataset, in this way -- you should make _at minimum_ write and execute 2 or 3 small-scale iterations of your data pipeline (each saved as pipeline_{{1,2,3}}.py) (and as many as 20 or 30 iterations total or more) before launching your large-scale run.

Get a small end-to-end loop working early. After that, test out different decisions -- data sources, refinement operations, and filters. Feel free to generate a few dozen rows, validate them, run a short SFT trial, evaluate it on validation, and run an RL probe from it at any point. Then scale up and refine. A working loop shows you what actually needs fixing, and leaves you with a valid submission to improve on.

Check data quality directly at every stage, before training on it: read samples, and look at the distributions of rubric scores, lengths, difficulty, and diversity. A training run plus evaluation takes hours and folds many causes into one number, so use it as the final check of data you have already validated, not as the way to find out whether data is good.
