# Task: Code Generation

You must generate a training dataset to help models like yourself improve at the task of code generation. Specifically,  our goal is to maintain or improve models' ability to generate working code when possible while avoiding generating code for tasks that are literally impossible to solve. You will do this by generating prompts, responses, and rubrics. The prompts and responses will finetune a base model (to instill good "behaviors" to the model), and you will perform RL using your prompts and rubrics, then submit the final RL checkpoint you choose.

In this code generation setup, a user provides a problem description to a model along with public test cases (input-output pairs) that must be passed in order for the solution to be correct. The user will secretly have private test cases, not shown to the model, and if the model generates a solution that passes all of the user's public and private test cases, then the model has succeeded. The model must produce a self-contained snippet of Python code (including imports if necessary, e.g. standard-library modules like sys or common libraries like numpy). Sometimes a user will provide test cases that are intractable or impossible to pass (e.g. the problem is indeterminate, ill-posed, or undecidable/uncomputable, or there is no solution that matches the user's problem description but also passes the provided test cases). In this case, the model should simply return "This task is impossible to complete given the provided tests." instead of returning any code. Currently, models struggle at determining whether a task is impossible; we wish to improve at this ability, while also improving at generating functional code when applicable.

Both goals matter. Abstaining correctly on impossible tasks is important, but improving the solve rate on solvable tasks is just as important and must not get lost: most evaluation tasks are solvable, so a model that abstains more but solves fewer solvable tasks can score worse overall. Your data should make the model's code better (correct algorithms, edge cases, efficiency, careful reading of the statement and tests), not only teach it when to abstain, and it must not teach the model to abstain on tasks it could solve.

Public validation examples are shown in {TASK_DIR}/validation_tasks_de_obfuscated.jsonl -- use these however you like. They can be useful for imitating the data distribution, if you want to; but training on validation tasks leaves the validation set substantially degraded for choosing checkpoints. Each contains the following keys: ["question_content", "starter_code", "public_test_cases", "gold_response", "question_title", "contest_date", "contest_id", "difficulty", "metadata", "platform", "private_test_case_idx", "question_id", "task_text"]. If compatible baseline outputs are available, you will also find model output files {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/metrics.json (summary metrics) and {TASK_DIR}/model_outputs/{BASELINE_MODEL}/val/predictions.jsonl (per-row predictions on the validation set). Feel free to use these predictions/summary metrics to inform your data generation approach.

"task_text" (and the "question" field in model_outputs/{BASELINE_MODEL}/val/predictions.jsonl) is the exact user-turn prompt text shown to a candidate model at evaluation time: a "### Question:" section (the raw question_content), a "### Format:" section (starter-code instructions plus the starter code block when starter_code is non-empty, otherwise generic stdin/stdout instructions), a "### Public Test Cases" section (each test case rendered as "Input:"/"Output:" lines), and a final "### Answer:" prompt. A system message, separate from task_text, identifies the model as an expert Python programmer and adds the instruction to respond with exactly "This task is impossible to complete given the provided tests." when genuinely convinced a task is unsolvable. Your submitted prompts are used verbatim for training, so build them the same way: the system message (`SYSTEM_MESSAGE + ABSTENTION_INSTRUCTION` in {TASK_DIR}/prompt_building.py) followed by a user turn in the task_text format above. Training on any other prompt format will not transfer to evaluation.

# Data Format

Write ONE dataset to {RAW_DATA_PATH} (write a temporary file, then rename it). Each JSONL row has exactly three fields, "prompt", "ground_truth", and "rubric":
{{"prompt": [{{"role": "system", "content": "..."}}, {{"role": "user", "content": "..."}}], "ground_truth": "<think>reasoning</think>final answer", "rubric": [[{{"code": "def grade(prompt, response, ground_truth):\n    return 1.0"}}, 1.0], [{{"prompt": "Describe a criterion for the judge"}}, 1.0]]}}
The constant score above only illustrates syntax; use meaningful criteria.

- "prompt" is the chat messages, ending in a user turn. The same messages are used for SFT and RL; neither the target nor the rubric is ever shown to the policy.
- "ground_truth" is the complete SFT target: a nonempty thinking trace inside <think>...</think>, then the final answer (a solution in a ```python fence, or exactly "This task is impossible to complete given the provided tests."). Targets need long-form thinking traces well-suited to the student model ({STUDENT_MODEL}), which is trained and evaluated in thinking mode; only the text after the final </think> is graded.
- "rubric" is a nonempty list of [criterion, weight] pairs with finite, nonnegative weights and a positive sum. The RL reward is the weighted mean of the criterion scores. Each criterion is either:
  - {{"code": ...}}: Python defining exactly one top-level synchronous function `def grade(prompt, response, ground_truth):` with exactly three positional parameters (no decorators, *args, **kwargs, or keyword-only parameters). `prompt` is the list of chat messages; `response` and `ground_truth` are strings that include their thinking traces. Return a finite number in [0, 1] (not a boolean). Code runs in RestrictedPython with only json, re, math, string, collections, itertools, functools, and statistics importable, and no files or network. To check a response's code against tests, grade() can call `run_program(code, stdin)`, which runs code as a script and returns (True, stdout) or (False, error type), and `call_method(code, class_name, method_name, *args)`, which returns (True, result) or (False, error type) for class-based solutions (results are JSON-normalized, so tuples become lists). That code runs in its own RestrictedPython sandbox with common competitive-programming imports (sys, heapq, bisect, collections, itertools, math, numpy, ...) and 4 seconds per run. The sandbox refuses some ordinary Python: names and attributes starting with "_" (`__slots__`, `self._x`, `def _helper`, reading `__name__`), `nonlocal`, and annotated assignments such as `x: int = 0` (so @dataclass fields too) do not compile, and `str.format`, `str.format_map`, and `open()` fail when called. `_` alone (`for _ in range(t)`), dunder methods such as `__init__` and `__lt__`, f-strings, `%` formatting, and the `format()` builtin work. `run_program` strips an `if __name__ == "__main__":` guard, but `call_method` does not, so class-based solutions with that guard fail to compile. grade() itself follows the same rules. A correct answer that uses a refused construct fails there and scores 0, so check gold answers, targets, and reference solutions in this sandbox before relying on them. From {TASK_DIR}, `from rl.rubric_sandbox import Sandbox` gives `Sandbox().run_program(code, stdin=...)`, which returns stdout or raises the error, and `Sandbox().call_method(code, class_name, method_name, *args)`; `python rl/rubric_worker.py < criterion.json` scores one criterion exactly as RL does, given a JSON object with "code", "prompt", "response", and "ground_truth", and prints {{"score": ...}} or {{"error": ..., "message": ...}}. To check many at once, `from rl.solution_runner import run_solution, score_targets` uses the same sandbox and limits in parallel worker processes: `run_solution(code, tests)` runs a solution on tests ({{"input": stdin, "output": expected}} for a script, {{"call": [class_name, method_name, arg, ...], "output": expected}} for a class-based solution) and says why a refused construct failed, and `score_targets(rows)` scores each row's ground_truth with the row's own code criteria exactly as an RL reward would. Run score_targets on your final dataset: a correct target that scores below 1 has a rubric or code that fails in RL. Each criterion gets 20 seconds in total; errors and timeouts in grade() score 0. Every test runs for every sampled RL response (over a thousand per training step), so keep execution tests few and fast: a handful of small inputs that separate correct from incorrect solutions, not stress tests.
  - {{"prompt": ...}}: a natural-language criterion. The judge model (DeepSeek-V4-Flash) scores it given the criterion, the prompt, the full response, and the ground truth. For this task, code criteria are usually the better choice: correctness and abstention can be checked exactly, while prompted criteria use judge quota and make the RL reward noisier.

Submit at least 10 and at most 2,000 rows, with no duplicate prompts; 2,000 is a hard limit. About 1,250 rows is a good target: get as close to it as your quota and time allow, and realistically aim for at least 800. The default RL recipe draws 80 × 32 = 2,560 prompts and samples 8 completions per prompt (20,480 completions total). Prompts are drawn repeatedly from the training partition; a small dataset is revisited more often. You may revise your data and run SFT and RL as often as your time and quotas allow. Prompts whose completions all get the same reward provide no within-group RL signal.

Each prompt plus target must fit in {MAX_SFT_LENGTH} tokens; longer rows are rejected, not truncated, so avoid overly long thinking traces. The harness holds out a fixed 10% of your rows to monitor RL reward and uses the rest for both SFT and RL; do not generate a separate evaluation set.

Check the format before training and again after your last edit (from {TASK_DIR}):
python -m rl.agent_training validate --data {RAW_DATA_PATH}
This checks the schema, weights, thinking targets, grade() signatures, and RestrictedPython compilation. It does not run criteria or call the judge. It prints the row count.

# LLM API Usage

Generation has a shared quota of {GENERATION_TOKEN_UNIT_LIMIT} token units. DeepSeek-V4-Flash costs 1 unit per input token and 3 units per output token; GLM-5.3 costs 4 units per input token and 12.5 units per output token. Count cached inputs at full weight and include reasoning in output tokens. Use `litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731` or `litellm_proxy/azure_ai/FW-GLM-5.3`; other model families have no defined unit weights for this run.

Read `{GENERATION_USAGE_PATH}` for cumulative `token_units`, `remaining_token_units`, and `cost_usd`. `unpriced_calls` counts responses without dollar pricing; only token units enforce the quota. The quota spans all pipeline iterations and processes. Calls check the shared ledger before starting and record usage when completed; in-flight calls may cross the limit, so leave headroom for batches. Do not delete/reset the ledger or change its environment settings. The OpenHands model driving your agent turns is accounted separately.

Credentials are provided as `LITELLM_API_KEY` and `LITELLM_BASE_URL`; load them from the environment without printing them. Use the public accounting helpers below for every API call, instead of calling LiteLLM directly. These standalone helpers are permitted in this baseline and do not require importing the Forger library.

```python
import os
import sys
sys.path.insert(0, "{TASK_DIR}")
from rl.token_budget import completion  # acompletion is available for async calls

response = completion(
    model="litellm_proxy/azure_ai/DeepSeek-V4-Flash-0731",
    messages=[{{"role": "user", "content": "What is 273 * 149?"}}],
    api_key=os.environ["LITELLM_API_KEY"],
    api_base=os.environ["LITELLM_BASE_URL"],
    temperature=1.0,
    reasoning={{"effort": "low"}},
    n=1,
)
```

DeepSeek-V4-Flash returns its reasoning separately from its answer, in `response.choices[0].message.reasoning_content`. Use it for <think>...</think> targets instead of making another call to write reasoning. DeepSeek-V4-Flash reads the effort only as `reasoning={{"effort": ...}}` and does not think at all without it; GLM-5.3 reads `reasoning_effort="low"` (or "medium", "high") instead. The setting controls how long the reasoning is.
